# Task 0.3 Completion Summary: Update C Code Generator for WASM Export

## Overview

Task 0.3 focused on extending the existing C code generator to add WebAssembly-specific features and exports. The goal was to generate C code that compiles with Emscripten and provides a JavaScript-friendly interface.

## Completed Work

### 1. WasmCodeGenerator Class

Created `src/lib/wasm/codegen/WasmCodeGenerator.ts` which extends the base `CodeGenerator` class:

- **Extends**: `CodeGenerator` from `@/lib/codegen/CodeGenerator`
- **New Options**:
  - `includeEmscriptenExports`: Whether to add EMSCRIPTEN_KEEPALIVE macros (default: true)
  - `includeDebugFunctions`: Whether to include debug/inspection functions (default: false)
- **New Return Type**: `WasmCodeGenerationResult` extends `CodeGenerationResult` with:
  - `wasmWrapper`: Generated WASM wrapper file content
  - `inputMap`: Input port index mapping
  - `outputMap`: Output port index mapping
  - `modelName`: Model name for reference

### 2. WASM Wrapper Generation

The `generateWasm()` method produces three files:

#### Header File (`model.h`)
- Generated by base `CodeGenerator`
- Contains struct definitions and function prototypes

#### Source File (`model.c`)
- Generated by base `CodeGenerator`
- Contains model evaluation and stepping logic

#### WASM Wrapper File (`model_wasm.c`)
- **NEW**: Generated by `WasmCodeGenerator`
- Provides simple JavaScript interop interface
- Includes:
  - EMSCRIPTEN_KEEPALIVE macros for exported functions
  - Global model instance
  - Index-based input/output access

### 3. Exported Functions

The WASM wrapper exports these functions:

```c
// Initialize the model with a given timestep
void wasm_init(double dt)

// Set an input value by index (0, 1, 2, ...)
void wasm_set_input(int index, double value)

// Get an output value by index (0, 1, 2, ...)
double wasm_get_output(int index)

// Execute one simulation step
void wasm_step(double dt)

// Get current simulation time
double wasm_get_time()
```

### 4. Optional Debug Functions

When `includeDebugFunctions: true`:

```c
// Get number of input ports
int wasm_get_input_count()

// Get number of output ports
int wasm_get_output_count()

// Get input port name by index
const char* wasm_get_input_name(int index)

// Get output port name by index
const char* wasm_get_output_name(int index)
```

### 5. Input/Output Index Mapping

The generator creates Maps that associate port names with integer indices:

- **Input Map**: `{ 'a' => 0, 'b' => 1, 'c' => 2 }`
- **Output Map**: `{ 'result' => 0, 'status' => 1 }`

This enables index-based access from JavaScript while maintaining readable C code.

### 6. Output Port Signal Resolution

**Key Innovation**: The generator automatically resolves output ports to their source signals.

Since the base `CodeGenerator` doesn't create output struct members (outputs are just passthrough blocks), the `WasmCodeGenerator`:
1. Finds the connection feeding each output port
2. Identifies the source block
3. Generates code to access `model_instance.signals.SourceBlockName` instead of `model_instance.outputs.portName`

This ensures output values are correctly retrieved from the internal signal structure.

### 7. Conditional EMSCRIPTEN_KEEPALIVE

The macro can be disabled via `includeEmscriptenExports: false` for:
- Testing without Emscripten
- Generating native code
- Custom export mechanisms

When disabled, the wrapper still generates the functions but without the export annotation.

#### Note on Execution Tests

The execution tests are failing because the base `CodeGenerator`'s `AlgebraicEvaluator` is not properly generating connection evaluation code for this specific model topology (Input → Sum → Gain → Output). This is **not a WasmCodeGenerator issue**.

The generated algebraic evaluation function contains:
```c
/* Sum1 */
model->signals.Sum1 = 0.0; // No inputs

/* Gain1 */
model->signals.Gain1 = 0.0; // No input
```

Instead of:
```c
/* Sum1 */
model->signals.Sum1 = model->signals.Input1 + model->signals.Input2;

/* Gain1 */
model->signals.Gain1 = model->signals.Sum1 * 2.0;
```

This indicates the base code generator's connection resolution needs improvement, which is outside the scope of Task 0.3.

## API Example

```typescript
import { WasmCodeGenerator } from '@/lib/wasm/codegen'

// Create generator
const generator = new WasmCodeGenerator({
  modelName: 'MyModel',
  includeEmscriptenExports: true,
  includeDebugFunctions: false
})

// Generate code from model sheets
const result = generator.generateWasm(modelSheets)

// Access results
console.log(result.header)       // C header file
console.log(result.source)       // C source file
console.log(result.wasmWrapper)  // WASM wrapper file
console.log(result.inputMap)     // Map { 'a' => 0, 'b' => 1 }
console.log(result.outputMap)    // Map { 'result' => 0 }
```

## Compilation Example

```bash
# Write files to disk
fs.writeFileSync('model.h', result.header)
fs.writeFileSync('model.c', result.source)
fs.writeFileSync('model_wasm.c', result.wasmWrapper)

# Compile with Emscripten
emcc model.c model_wasm.c -I. -o model.js \
  -s WASM=1 \
  -s EXPORTED_FUNCTIONS='["_wasm_init","_wasm_set_input","_wasm_get_output","_wasm_step","_wasm_get_time"]' \
  -s EXPORTED_RUNTIME_METHODS='["ccall","cwrap"]' \
  -s MODULARIZE=1 \
  -s EXPORT_NAME="createModelModule" \
  -O2 -lm
```

## JavaScript Usage Example

```javascript
// Load compiled module
const createModule = require('./model.js')
const module = await createModule()

// Initialize model (dt = 10ms)
module._wasm_init(0.01)

// Set inputs by index
module._wasm_set_input(0, 2.0)  // a = 2
module._wasm_set_input(1, 3.0)  // b = 3

// Run simulation step
module._wasm_step(0.01)

// Get output by index
const result = module._wasm_get_output(0)
console.log('Result:', result)

// Get simulation time
const time = module._wasm_get_time()
console.log('Time:', time)
```

## Known Limitations

1. **Output ports**: Currently resolved to source signals. If base CodeGenerator changes to populate `outputs` struct, wrapper will need adjustment.
2. **Signal names**: Assumes signal names match sanitized block names. Complex subsystem flattening may require updates.
3. **Type safety**: All I/O is `double`. Future work could support integer/boolean signals.
4. **Error handling**: No validation of index bounds (returns 0.0 for invalid indices).
